可以把整个项目理解成一句话：

> 先把剧情整理成一张“可计算的表”，再用一些简单的数学方法寻找重复、相似、变化和转折，最后回到原文解释这些结果。

NLP 不等于“让电脑真正理解文学”。在这个项目里，NLP 更像一套测量工具：它帮你发现人读全文时可能注意到、但不容易系统统计的模式。

整个过程可以分成六步。

1. 先把剧情变成规整的数据

现在的原始材料不是整齐的小说，而是 Wiki 页面里的模板、标题、角色标签、选项、短信、旁白和分支。

所以第一步不是分析，而是清洗和结构化。最终每条记录大致像这样：

```
{
  "version": "3.7",
  "task": "魔女的孤诣课题",
  "step_title": "揭露隐秘的记忆",
  "kind": "dialogue",
  "speaker": "昔涟",
  "canonical_speaker": "昔涟",
  "text_clean": "我一直以为，自己是逐火之旅的讲述者。",
  "order": 23500
}
```

这一步解决的是：

- 这句话是谁说的？
- 它属于哪个版本和任务？
- 它是对白、旁白、选项还是短信？
- 它在剧情中的先后位置是什么？
- 角色的不同称呼是不是同一个人？

如果这一步不可靠，后面统计出来的结论也不可靠。

你现在已经完成了这一步，而且完成得相当充分。可以把它看成建立了一个“剧情数据库”。

1. 决定电脑到底要观察什么

文学分析最容易犯的错误，是直接说“分析情绪”“分析命运”“分析悲剧感”，但这些概念太大，电脑无法直接计算。

所以要把它们拆成可观察的变量。

例如，“神谕被角色认领”可以拆成：

- 神谕原文出现在哪里；
- 谁再次提到它；
- 提到时是否保留原句；
- 是否改成了第一人称；
- 是别人转述，还是角色自己宣告；
- 这种引用发生在剧情前期还是结尾。

“叙事冲击点”可以拆成：

- 是否出现新身份或新关系；
- 是否揭示了过去的真相；
- 是否让前文某个意象重新获得意义；
- 是否改变了故事的时间或叙述视角；
- 是否完成了长期铺垫；
- 这之后剧情状态是否发生持续变化。

这一步其实是整个项目最重要的思考工作。算法只是后面的计算手段。

1. 神谕分析是怎么做的

神谕分析可以分成四个小问题。

第一，建立神谕表。

例如记录：

| 字段     | 内容                     |
| -------- | ------------------------ |
| 神谕     | 原始预言句               |
| 对象     | 哪位黄金裔               |
| 隐喻     | 表面出现的词             |
| 所指     | 注音或剧情明确指向的对象 |
| 首次出现 | 版本、任务、步骤         |
| 兑现位置 | 后续剧情中的对应场景     |
| 兑现类型 | 字面、反转、错位         |

这相当于先把文学材料整理成一组“事件记录”。

第二，寻找神谕可能对应的剧情片段。

假设有一句神谕，要在两万多条台词里找最可能的兑现片段。可以从简单方法开始。

最简单的是关键词匹配：

```
神谕：黄金、沐浴、最后一次
剧情片段：黄金浴池、最后一次、阿格莱雅
```

如果两段共享的词很多，就认为可能相关。

但隐喻往往不会重复原词，所以还需要语义相似度。

在数学上，可以把一段文字表示成一个向量：

```
神谕 → [0.2, -0.1, 0.7, ...]
剧情片段 → [0.3, -0.2, 0.6, ...]
```

如果两个向量方向接近，就说明它们可能表达相近的内容。最常用的计算是余弦相似度：

\[ \cos(\theta)=\frac{x\cdot y}{\|x\|\|y\|} \]

它不关心两段文字长度完全相同，而是看它们在语义空间中的方向是否相近。

你可以把这理解成：

- 关键词匹配：有没有说过相同的词；
- 向量匹配：即使没说相同的词，是不是在说相似的事。

第三，追踪神谕被谁引用。

这一步主要依赖你已经整理好的角色和剧情顺序，不一定需要复杂模型。可以把引用分成几类：

```
神谕原文出现
→ 旁白转述
→ 他人解释
→ 角色本人引用
→ 角色主动认领
→ 结局宣告或改写
```

这其实是一个时间序列问题。你可以画出每条神谕的“传播轨迹”，看它怎样从外部命运变成角色自己的语言。

第四，比较语言风格。

这里的“风格”不是文学价值判断，而是一些可以数的特征：

- 平均句长；
- 抽象名词比例；
- “将、必、终”等情态词比例；
- “汝”等特殊人称比例；
- 排比、重复和命令句；
- 第一人称和第二人称的使用；
- 角色引用神谕时是否越来越接近神谕原文。

例如可以比较三组文本：

```
神谕原文
普通对白
角色引用神谕的对白
```

如果第三组在句式和词汇上更接近第一组，你就可以讨论“角色如何借用神谕的语言来表达自己”。

1. 叙事显著性检测是怎么做的

这里最好不要直接说“识别观众什么时候想哭”，因为文本里没有观众情绪这个变量。

更准确的问题是：

> 哪些片段使故事状态发生了明显变化？

先建立一个人工标准。比如每个场景标一个等级：

```
0：普通推进
1：有局部信息或关系变化
2：叙事状态明显变化
3：重大转折，或重新解释了前文
```

还可以标记转折类型：

```
identity       身份揭示
memory         记忆恢复或重构
prophecy       神谕兑现
relationship   关系变化
world          世界规则揭示
sacrifice      牺牲、死亡、告别
motif          母题或重复意象回收
```

然后做两个检测器。

第一个是普通基线。

它只看当前片段里有没有明显信号：

- 死亡、牺牲、告别、失去；
- 否定和负面情绪词；
- 感叹、停顿、短句；
- 第一人称脆弱表达。

可以简单地给每个片段打分：

\[ S_{\text{普通}} = \text{冲击词数量} + \text{负面词数量} + \text{停顿和短句分} \]

它的优点是简单、容易解释；缺点是只看局部词汇。

第二个是优化版本。

它不仅看当前片段，还看这个片段前后发生了什么：

- 当前片段和前一段的语义是否突然变化；
- 是否出现新的身份、关系或世界规则；
- 角色名称或形态是否发生变化；
- 是否从现在切到回忆、循环或未来；
- 旧神谕、歌谣、称呼是否被重新提起；
- `repeat_kind` 是否显示母题或仪式性重复；
- 这段之后的剧情状态是否持续改变。

可以写成：

\[ S_{\text{优化}} = S_{\text{普通}} + \lambda_1\text{语义突变} + \lambda_2\text{身份变化} + \lambda_3\text{前文回收} + \lambda_4\text{状态变化} \]

这里的 \(\lambda\) 是各项特征的权重，可以先人工设定，再用标注数据调整。

昔涟诞生剧情就是优化版本应该找出来、而普通版本可能漏掉的案例。

它的冲击并不主要来自“死亡”“牺牲”等词，而来自：

- 昔涟的身份从同行者变成被解释的对象；
- “诞生之地”重新定义了她的来源；
- 小妖精歌谣、记忆记录和德谬歌被串联起来；
- 讲述者和听众的位置发生了反转；
- 前面很多零散内容突然获得统一解释。

也就是说，普通方法看到的是“这一段用了哪些强烈词”，优化方法试图看到“这一段之后，故事已经变成了什么样”。

1. 怎么判断优化方法真的更好

你不需要证明它“理解了文学”，只需要做一个小型、可检查的对比实验。

先人工标注 40–80 个场景，形成一个小测试集。然后让两个方法分别给所有场景排序。

比较：

- 普通方法排在前 10 的片段，有多少是真正的显著点；
- 优化方法排在前 10 的片段，有多少是真正的显著点；
- 昔涟诞生、神谕兑现、身份揭示等案例有没有被找回；
- 两种方法分别会漏掉什么、误报什么。

例如：

```
普通方法 Top 20：12 个明显死亡/告别片段，漏掉 3 个身份揭示
优化方法 Top 20：10 个明显事件，找回 3 个身份揭示和 2 个母题回收
```

这种结果就能说明：结构特征确实补充了词面方法。

这里的指标可以很简单：

- `Precision@10`：前十名里有多少是真的；
- `Recall@20`：人工标出的显著点有多少被前二十名找回；
- 成功案例和失败案例分析。

如果样本太少，不要把它包装成高可靠分类器。写成“候选排序 + 人工验证”完全合理。

1. HMM 和知识图谱放在哪里

你不需要为了课程大纲强行使用所有方法。

HMM 可以这样理解：

> 它适合描述一个对象如何从一种状态转移到另一种状态。

如果你想使用它，可以把神谕引用过程表示成：

```
未出现
→ 被转述
→ 被解释
→ 被角色引用
→ 被主动认领
→ 被兑现
```

HMM 的任务就是根据观察到的台词，估计当前更可能处于哪种状态。它适合作为一个小型扩展，但不是项目核心。

知识图谱可以这样理解：

> 它不是主要算法，而是一张带关系的结构化地图。

比如：

```
神谕 ——属于—— 黄金裔
神谕 ——包含—— 隐喻词
隐喻词 ——指向—— 角色或事件
角色 ——引用—— 神谕
神谕 ——兑现于—— 场景
```

这张图可以用来查询：

- 哪些神谕被本人引用过；
- 哪些神谕被其他角色解释过；
- 哪些隐喻在兑现前已经出现；
- 哪些神谕的兑现方式是反转。

所以它可以作为结果展示和课程内容对应，不必变成一个复杂的系统。

1. 最后整个项目可以这样组织

最清晰的结构是：

```
语料工程
  ↓
神谕抽取与隐喻解码
  ↓
神谕—事件语义匹配
  ↓
神谕引用轨迹
  ↓
神谕语体与角色引用语体对比
  ↓
叙事显著性检测扩展
  ├─ 普通冲击点检测
  └─ 结构增强检测
  ↓
案例分析与结论
```

最终你要回答的不是“我用了多少 NLP 算法”，而是两个问题：

1. 神谕如何通过固定语言形式进入剧情，又如何被角色重新解释？
2. 文本中的重要转折，是否不能只靠强烈词汇识别，而需要观察身份变化、前文回收和叙事状态变化？

前一个问题是项目主线，后一个问题是方法扩展。这样方法数量虽然不多，但每种方法都有明确用途，也不会被 NLP 的名词淹没。
