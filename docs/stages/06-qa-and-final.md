# 06 · 质检与最终交付：三份 QA、外部复核与 amphoreus.final

## 1. 目标与意图

到 v2 阶段，手里有「v1 语料 + v2 归一清洗版」，但**没有任何独立质检**：
数字都是生成脚本自报的，文档里的声明数字（说话人数、`他/她` 处数、渲染命中率）也没有核对过。
本阶段要做四件事：

1. **独立质检**：只用只读脚本重新统计、自检、列出问题，不信任既有文档；
2. **修问题**：按严重度排序，把「会丢数据」的解析缺陷修掉（→ v3.1）、把「归一覆盖率」补上（→ alias v2）；
3. **外部复核**：让外部模型交叉比对配置与文档，抓人眼容易漏的逻辑错误；
4. **交付**：产出最终语料 `amphoreus.final.jsonl` + 交付/终检报告，给出可验收的最终数字。

## 2. 方案

| 手段 | 做法 | 为什么需要 |
|---|---|---|
| 统计报告 | `tools/report-corpus.js` 重新统计全部维度 | 防止「文档数字」与「文件实际」脱节 |
| 结构自检 | id/order/idx 连续性、版本单调、字段缺失率、文本纯度 | 结构错误会让所有下游分析失效 |
| 未归一清单 | 逐个 speaker 列出句数/版本/例句/建议 | 扩表不能凭感觉，必须按证据逐条补 |
| 问题清单 | 按高/中/低严重度排序 + 影响面 + 建议 | 决定修复优先级与是否改基线 |
| 外部复核 | Gemini 交叉比对 v2 配置与 5 份文档 | 配置里的逻辑错误（关系方向、越界版本）人工评审易漏 |
| 最终校验 | `tools/finalize-corpus.js` 的 `final-qa` | 交付前逐项打勾 |

**约束**：QA 脚本**只读**；不修改 `data/corpus|config|raw`；不联网；不改已有文档（只写报告）。

### 3.2 修复：v3.1 解析补全（24,206 → 26,332）

按清单 #1/#2/#4 与「`:` 行丢弃 / 短信未解析」等 7 类缺陷，用 `tools/build-corpus-v31.js` 修：

- 行首 `:` 场景旁白 + 选项块内旁白：**1,817 + 209** 条；
- `{{短信选项}}` 14 块：`sms_option` 32 + `sms` 98（含内联对白 32）；
- 模板平衡展开：`{{`/`}}` 残留 216 → **0**；
- narration 内嵌说话人：拆分 **855** 条；
- 伪说话人：2 → 0；
- `step_title`：回退 1,554 → 推断 1,706 / 缺失 **0**。

结果 **26,332 条 / 566,798 字**，v1 的 24,206 条 **100% 可用 `v1_id` 回接**且相对顺序不变（详见 `03`）。

### 3.3 修复：归一扩表与外勘（82.54% → 99.37% → 交付 97.58%）

- `speaker-alias.v2.json`：canonical 38 → 124，覆盖 v1 语料 **22,944 / 23,090 = 99.37%**，只剩 9 条/3 标签；
- 外部复核（Gemini）后 `speaker-alias.v3.json`：修正 5 类勘误、4 个架构拍板、9 条未归一处置
  （清单见 `docs/speaker-alias-errata.md`；细节见 `04`；
  **其中「1 处可读性问题」在仓库内未找到对应记录，标注「待确认」**）；
- 最终语料换到 v3 配置 + v3.1 语料后，命中 **23,460 / 24,041 = 97.58%**：
  低于 99.37% 并非退步，而是**语料变大了**（v3.1 新增 951 条非空 speaker，其中 5 百多条是未登记的新标签，不猜）。

### 3.4 交付：`tools/finalize-corpus.js`

只做四件事：① 说话人归一（canonical/form）；② `text_clean`；③ `view`；④ 去重标记。
不改原文、不改输入文件、幂等。输入 = `amphoreus.v31.jsonl` + **`speaker-alias.v3.json`**
（注意：`data/README.md` 与 `final-delivery.md` 的说明写的是 v2 配置，与实际脚本不一致，见 §6）。

`data/reports/final-delivery.md` + `final-qa.md` 记录最终指标。

## 6. 踩过的坑与修正（含文档间数字不一致清单）

1. **「未命中全在折叠块内」的结论不成立**：README 的 41 条抽检说未命中 13 条全在 `{{折叠}}` 块，
   但 QA 用整页 849 条核对发现：非折叠记录**也有约 1/7**（106 条）在 `innerText` 里找不到。
   修正：把结论改成「解析结果比渲染可见内容更全，但未命中不能全部用折叠解释，需人工抽样复核」。
2. **README 数字两处失真**：`他/她` 153 → 实测 117 处；`*强调*` 282 → 实测 342 对。
   修正：在 QA 报告与 README 已知问题里按实测更新，并保留「此前误记」的说明。
3. **「链一致性违例 0」是口径造成的错觉**：v3 自检只查**边方向**；
   换成「简单相邻链」口径就有 8 处不吻合、2 条反向边（3.4 是分支页结构）。
   修正：在 QA 报告与 README 都注明口径，避免下游把 `prev/next` 当相邻页用。
4. **未归一数有两套口径**：严格口径 434 个 / 4,043 条；归一引擎口径 435 个 / 4,032 条。
   修正：两份文档各自标清引擎，`speaker-alias-changes.md` §0 统一解释差异。
5. **去重口径随语料版本变化**：v1 上 495 组 / 901 条；final（v3.1 语料）上 626 组 / 1,120 条。
   修正：不强行统一，按「检测时所用语料版本」标注。
6. **`data/README.md` 的最终数字没随配置 v3 更新**：
   - 写「23,455 / 97.56%」，实测 **23,460 / 97.58%**，差 5 条恰好等于外勘 H 项处置的记录数
     （先祖之灵 4 + 古怪的弈者 1），推断该数字停留在配置 v2 的运行结果；
   - 写「由 v31 + `speaker-alias.v2.json` 生成」，实际 `finalize-corpus.js` 读的是 **`.v3.json`**
     （实测 final 里 `萨姆→流萤+form=萨姆`、`先祖之灵→generic_npc`、`古怪的弈者→来古士`，只有 v3 配置才有）；
   - 写长度「P90 42 / P99 67」，实测 **43 / 69**（`text` 口径）；写 `wt-cache` 「~4 MB」，实测 **2.48 MB**；
   - 写「v1 字段逐字节保留」，但 v2 有 19 条舞台指示 `kind` 改判（`corpus-pipeline.md` §3.6 已说明）。
   修正：本目录 `README.md` 的「最终数字口径速查」按实测写，并在此列出差异；建议同步修 `data/README.md`。
7. **外勘记录内部小矛盾**：`speaker-alias-errata.md` 表里 F 写「9 条 literal 映射」，说明文字写「10 组 medium 推断」。
   修正：标注「待确认」，不影响 final（v3 配置已落盘，实测按实际命中运行）。
8. **交付报告的表述瑕疵**：`final-delivery.md` 遗留项写「空 `text_clean`：0 条（源文本在 v31 中已丢失，建议回原始 wikitext 补）」
   ——前半句是 0 条，括号里的解释却像在描述有丢失，容易被误读。修正：在 `final-qa.md`/本文件按实测澄清：
   final 空 `text_clean` 实测 0 条，不影响交付。
9. **教训**：QA 只读脚本很有价值——它一次就抓出 README 里 3 个错数、1 个伪结论、2 个口径陷阱。
   写报告引用数字时，一律以「生成脚本 + 实测复核」为准，不以旧文档为准。
