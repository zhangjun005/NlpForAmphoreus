# 01 · 数据源调研：渠道评估与「BWiki + SMW」的选定

## 1. 目标与意图

确定阶段 00 定下的 67 页主线剧情**从哪里取、能否稳定复现、是否合规**。具体要同时满足：

1. **正文可得**：每页要拿到「说话人 + 台词 + 旁白 + 步骤标题」的原始内容，而不是被拍平的一整段；
2. **可批量**：67 个页面能自动化下载，可重跑；
3. **说话人可补**：除正文外还要有一套「角色称呼/别名/称号」的来源渠道；
4. **合规**：只读采集公开页面，语料不公开发布。

调研分两条线：**正文数据源**（游戏剧情文本）与**称呼数据源**（角色昵称/外号/称号）。

## 2. 方案：候选渠道

### 2.1 正文数据源（4 个候选，来自 `docs/chatWithGemini.md`）

| 渠道 | 思路 | 预期优势 | 预判风险 |
|---|---|---|---|
| A. Hakush.in / Yatta.top | 数据库站点已把任务对话树拍平成 JSON，抓其 XHR 接口 | 结构化、已带 speaker、10 分钟可跑 | 需知道任务 ID / 站点改版；讨论稿作者自注「我发现不太行」 |
| B. BWiki 剧情页爬虫 | 抓「开拓任务」页与各任务页 HTML，用 BeautifulSoup 取 `p`/`tr` | 纯文本、带角色名排版 | 页面可能由模板渲染，DOM 结构与预期不同 |
| C. 社区「剧情重构」工具 | `StarRail-Story-Parser` 类工具读解包数据（`TextMapCHS.json`、`QuestData.json`）自动导出线性剧本 | 最全、最原始、天然带说话人与分支 | 需本地已有 `StarRailData` 解包仓库；合规风险 |
| D. B 站视频字幕 | 拉官方 CC / AI 字幕接口（`api.bilibili.com/x/player/v2`）得带时间戳对白流 | 5 分钟、语料天然线性 | 字幕**无说话人**；需登录与风控；AI 字幕有错字 |

### 2.2 称呼数据源（候选更多，`docs/speaker-aliases.md` §〇）

## 3. 实施：逐渠道实测与结论

### 3.1 Hakush / Yatta（否决）

- 讨论稿把它列为「最推荐」，但标题后紧跟一句作者实测结论「**我发现不太行**」。
- 仓库内**没有**对应的探针脚本或抓包记录（`tools/` 无相关文件），无法复现，按未采用处理。

### 3.2 BWiki（采用，但改了技术路线）

实测三步：

1. **抓「开拓任务」列表页 HTML**（`tools/fetch-bwiki.js`）→ `data/raw/bwiki-kaiTuoRenWu.html`，实测 **514,158 字节**。
   结构分析结论：该页正文是 Semantic MediaWiki 的 `{{#ask:}}` **服务端渲染结果**，
   **没有 `table`/`tr`** → 讨论稿建议的 `soup.find_all(['p','tr'])` 完全落空。
2. **看同页 wikitext**（`data/raw/bwiki-kaiTuoRenWu.wikitext`，仅 **3,407 字节**）：
   全部内容只有 7 个章节标题 + 几条 `#ask` 查询语句，**不含任何任务条目**。
   也就是说列表页的「条目」只存在于渲染结果与 SMW 数据库中，**爬 HTML 或爬 wikitext 都拿不到索引**。
3. **改用 MediaWiki API**：`action=ask` 直接向 SMW 要结构化结果（任务名 + 系列 + 版本 + 编号 + 类型），
   `action=parse&prop=wikitext` 逐个任务页取原始 wikitext。两条路都是官方 API、只读、可重跑。

### 3.3 社区解析工具（否决）

需要本地已克隆 `StarRailData`（游戏解包数据），且要处理 `NextActID` 条件分支、Hash Key 二次索引。
本项目目标是「可复现地把公开 wiki 文本变成语料」，引入解包数据会带来**合规不确定性**与额外依赖，
故不采用。`tools/` 中也没有相关代码。

### 3.4 B 站字幕（否决）

字幕接口返回的是「一句一句纯对白 + 时间戳」，**没有说话人字段**，
而说话人正是本语料最关键的元数据（后续所有 NLP 分析都依赖它）。
另外拉取需要 `cid`/`bvid` 与可能的登录/风控处理，稳定性不如 wiki。
补充：字幕只能当「辅助校对源」，不能当主数据源。

### 3.5 称呼来源的实测结论

- **BWiki 角色页**：只覆盖「进卡池角色」，NPC/非卡池角色会 MISSING。
  用 `tools/fetch-nicknames.js` 硬编码 35 个页名批量抓：实测产出 31 个角色页段（其中「缇宝」重复 3 段，
  因 缇安/缇宁 重定向到缇宝）+ 3 个 `NO_NICK_FIELD`（帕姆/来古士/塞涅卡：页面存在但无「昵称/外号」字段）
  + 1 个 `MISSING`（荒笛：页面不存在）→ `data/raw/nicknames.txt`（实测 10,896 字节）。
  ⚠️ `data/README.md` 与 `handoff.md` 把这一结果概括为「31 命中 + 4 个 MISSING」，实际标记是
  **3 NO_NICK_FIELD + 1 MISSING**，以文件为准。
  页面里 `昵称/外号` 常带 `{{黑幕|…}}`（剧透/黑话）与 `〔注：谁这么叫〕`，需要解析。
- **BWiki 设定页 `翁法罗斯`**：调研中「新发现，信息量最大」——十二黄金裔、`X爵` 爵位体系、
  前世黄金裔、泰坦与黄金裔的对应、迷迷的官方定义都在这里，且可按 `section=` 精确定位小节。
- **萌娘百科**：页面能打开，但 **API 被禁**，整页抓取成本高（HTML 结构复杂），只在少数角色上人工查证。
- **Fandom 中文 wiki / 中文维基百科**：本地 DNS 解析到非公网 IP，请求被拦，**直接排除**。
- **百度百科**：可正常访问，用于补「无角色页」的角色（如帕姆的别名、黄金裔对照表）。

## 5. 决策与取舍

| 决策 | 取舍 | 理由 |
|---|---|---|
| 正文用 **Wikitext API**，不用 HTML 正文 | 放弃「用 BeautifulSoup 拿渲染文本」 | 列表页无 `table/tr`；任务页正文用 wikitext 才有说话人/模板结构，渲染文本会把结构拍平 |
| 索引走 **SMW `action=ask`** | 放弃「解析列表页」 | 列表页 wikitext 只有查询语句，条目不落在页面里 |
| 用**官方 API** 而非第三方数据库站点 | 放弃 hakush/yatta 的「已拍平 JSON」 | 无稳定接口记录、无法复现；官方 API 可长期重跑 |
| 不引入解包数据 | 放弃「最原始、最全」 | 合规不确定 + 依赖重；wiki 已能覆盖主线全部对白 |
| 称呼多渠道交叉 | 放弃「只用 BWiki 角色页」 | 角色页只覆盖卡池角色；NPC/正式爵位/设定页信息必须另找 |
| 语料不入 git | 放弃「把数据一起交付」 | 见下节合规结论；用 `wt-cache/` + 脚本保证可复现 |

**合规结论**（`data/README.md` §五）：BWiki 内容按 CC BY-NC-SA 4.0 提供，游戏文本著作权属米哈游；
本项目仅在课程/研究范围内做文本分析，**不公开分发** `data/corpus/` 或 `wt-cache/` 原文；
`.gitignore` 忽略 `data/corpus/`、`data/raw/`、`data/shots/`、`data/reports/`，仓库只入库代码、配置与文档。

## 6. 踩过的坑与修正

1. **想当然沿用讨论稿的 BeautifulSoup 方案** → 实测 `p`/`tr` 零命中。
   修正：抓 HTML 后先做结构统计，发现正文是 `#ask` 渲染结果，改走 SMW API。
2. **以为列表页 wikitext 里有任务条目** → 实际只有 3.4 KB 的章节 + 查询语句。
   修正：放弃「解析列表页」，索引只认 SMW 结果。
3. **仅靠 SMW 分类查询会漏页**：`[[分类:开拓任务]][[任务地区::翁法罗斯]]` 返回 74 页，
   但「魔女的镜中回天」剧情发生在黑塔空间站、归属 3.2 系列，不在该分类组合里。
   修正：从「开拓任务」页的第四幕章节卡片补漏 1 页 → 索引变 **75 页**（`tools/audit-section.js` 用于核对两者差异）。
4. **把萌娘百科当常规 API 源** → API 被禁，只能整页抓；修正为「只做人工查证，不进自动管线」。
5. **本地 DNS 问题被误判为站点故障**：Fandom 与中文维基都解析到非公网 IP 导致请求失败，
   排查后确认是本地网络策略而非目标站点不可用。修正：直接排除这两个渠道，不再耗时重试。
6. **抓取礼节差点踩线**：初期想并发拉页面。修正：统一 UA（Chrome 140）、任务页 180ms/页、
   角色页 150ms/页、重试 3 次指数退避、超时 25–40s，全部脚本只读采集（见 `docs/handoff.md` §6.8）。
