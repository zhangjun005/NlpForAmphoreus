# 00 · 方向评审：四个 NLP 方案与「先做语料」的判定

## 1. 目标与意图

项目起点不是「写一个 NLP 模型」，而是「给这门课程选一个**有内容、可解释、又能体现方法深度**的题目」。
选材对象是游戏《崩坏：星穹铁道》的翁法罗斯（Amphoreus）主线剧情——它有希腊悲剧式的神谕叙事、
神权政治博弈、以及「泰坦 / 黄金裔 / 凡人」三层角色结构，文本天然带**说话人标签、幕与段落、
诗体预言与口语对白交错**等元数据，很适合做可解释的 NLP 分析。

本阶段的意图是：

1. 先发散出若干候选研究方向，再**逐条评估可行性**（数据能不能拿到、方法是否可复现、结论是否可解释）；
2. 判定这些方案对数据的**共同前置依赖**；
3. 决定项目第一阶段的真实目标——是直接做分析，还是先把「可用的结构化语料」造出来。

## 2. 方案：四个候选选题

原始讨论记录见 `docs/chatWithGemini.md`（2026-10-23 16:03，人工保存的方向讨论稿）。
其中提出四个方案，均为「叙事 + 算法」结合型选题：

### 方案 1 · 悲剧神话的「宿命–抗争」正交基底 + 角色心智轨迹

- **切入**：翁法罗斯主题是「神谕预言 vs 凡人抉择」，普通情感分析（正/负）无法表达这种哲学张力。
- **方法**：用剧情全文训练 Skip-gram 词向量（`vector_size=128`、`window=5`）；用极性子集做质心差
  构造两条语义轴（宿命轴、秩序轴，各取正负种子词质心差后归一化）；再按角色/章节对句向量做平均池化，
  投影到二维相空间，得到角色立场随剧情推进的轨迹。
- **展示**：角色二维「性格/立场相空间」演化图；再用向量代数检验「泰坦 − 神圣 + 凡人」这类类比。
- **数据依赖**：需要**按幕/章节切分**且**带说话人**的台词序列。

### 方案 2 · 泰坦神权与城邦同盟：动态社会拓扑与权力中心演化

- **切入**：多城邦、多派系的政治斡旋隐藏在台词里，可从对话反推派系与权力中枢变迁。
- **方法**：以**剧本自带的 Turn/Scene** 为单位切共现窗口（而非全文滑窗）；用 PPMI 加权建角色共现图，
  剥离主角「逢人必聊」的高频噪声；用 Louvain / Leiden 做社区发现，逐幕计算中介中心度与 PageRank。
- **展示**：随剧情推进的 4–5 张关系拓扑网络图；关键角色「话语权指数」时序折线。
- **数据依赖**：需要**场景/轮次边界**与**规范化的说话人**（否则同一角色被拆成多个节点）。

### 方案 3 · 神谕预言与现实的「跨文体语义对齐」伏笔解码器

- **切入**：剧中穿插晦涩的预言诗/石碑铭文，数幕之后与现实事件呼应，字面重合度极低。
- **方法**：先把语料切成《预言/神谕集》与《现实叙事集》两个子集；用 TF-IDF 加权 +
  Word Mover's Distance / Soft-Cosine 计算神谕与各事件段的语义传输距离；输出相似度热力图。
- **展示**：预言–事件匹配热力图，标出「哪条预言对应第几幕的哪个转折」。
- **数据依赖**：需要**文体切分标注**（哪些行是预言诗、哪些是现实对白）——语料中并不存在该字段。

### 方案 4 · 希腊式城邦修辞学：角色说话风格指纹与身份分类器

- **切入**：神明/泰坦、哲人、平民、开拓者的语体反差极强，可做「风格指纹」。
- **方法**：词性分布、TTR 词汇多样性、句长均值/方差、古语典故词频等特征；用 TF-IDF + 卡方/对数似然比
  提取每个角色最具排他性的「风格词」；再用 PCA/t-SNE 聚类、逻辑回归/朴素贝叶斯做匿名台词归属分类。
- **展示**：角色风格雷达图；匿名台词盲测混淆矩阵。
- **数据依赖**：需要**足量、且说话人已归一**的每角色台词（长尾角色样本太少会不稳定）。

### 四方案对照（`chatWithGemini.md` 原表摘要）

| 方案 | 趣味度/契合点 | 核心算法 | 实现难度 | 汇报亮点 |
|---|---|---|---|---|
| 1 宿命–抗争投影 | 紧扣悲剧内核 | 词向量、正交化、空间投影 | 中 | 2D 相空间轨迹图 |
| 2 动态社会拓扑 | 城邦政治权谋 | PPMI、Louvain、中心度 | 低~中 | 交互式关系网络 |
| 3 预言伏笔对齐 | 叙事隐喻机制 | WMD、Soft-Cosine | 中~高 | 隐喻热力图 |
| 4 角色修辞指纹 | 古典语体反差 | 词性熵、卡方、风格特征工程 | 低 | 雷达图 + 盲猜 Demo |

## 3. 实施：从「选题」到「项目定位」

评审结论不是选一个方案，而是发现四个方案**有同一个硬前置**：

- 方案 1 需要「按幕/章节 + 说话人」的台词序列；
- 方案 2 需要「场景边界 + 规范化角色名」；
- 方案 3 需要「文体切分」；
- 方案 4 需要「说话人准确率高、长尾有样本」。

而当时手上**没有任何结构化数据**：只有「去 wiki 上人工读剧情」这一条路。
因此项目定位被改写为：

> **这是一个语料工程项目，不是分析项目**：目标是「可复现地把 wiki 文本变成干净可用的结构化语料」。
> 分析代码尚未开始写，四个方案只作为后续方向参考。

依据：`docs/handoff.md` §1.1 原文、`data/README.md` 开篇定位。

同时定下**范围决策**（不再扩大）：只做主线「开拓任务」3.0–3.7 的 8 个系列任务、67 个任务页；
不纳入翁法罗斯地区的 7 个冒险任务、4 个活动任务、同行/日常任务、支线，以及书籍/短信/道具文案。
四条理由：

1. 活动剧情多为整活/番外，语体与主线不同；
2. 活动背景时间可能早于当前版本（一个版本的活动可能对应前几个版本的时间点），时间线不可靠；
3. 支线多数与黄金裔关系不大；
4. 散落文本（书籍/短信/道具文案）时间线更乱。

由此推出项目实施顺序（后续 6 个阶段即按此执行）：
**数据源调研 → 抓取 → 解析迭代 → 角色称呼集合 → 归一清洗 → 质检交付**。

## 5. 决策与取舍

| 决策 | 取舍 | 理由 |
|---|---|---|
| 先做语料，后做分析 | 放弃「一上来就训练模型」的路线 | 四个方案都依赖结构化语料，先做分析只能手抄/小样本，结论不可复现 |
| 只做主线 67 页 | 放弃活动/支线/书籍/短信（范围更小） | 时间线可靠性与语体一致性优先；范围小才能把质量做上去 |
| 项目定位为「语料工程」 | 放弃在课程报告里宣称「完成了四个 NLP 分析」 | 只记录真实发生的事，避免把提案写成成果 |
| 四个方案全部保留为「后续方向」 | 不删任何一个 | 报告需要「从选题到落地」的完整链条；语料交付后四者都可做 |
| 不做游戏解包 | 放弃「拿最原始、最全的文本」 | 解包需处理 `NextActID` 条件分支与 Hash Key 二次索引，成本高且合规风险大（见 `01`） |

## 6. 踩过的坑与修正

1. **把「AI 给的建议」当成了「已验证的方案」**。`chatWithGemini.md` 里的四个方案写得像实施方案，
   但其中的量化目标（如方案 4 的「85%+ 准确率」）只是**提案期望值**，从未跑过。
   修正：在 `handoff.md` §1.1 明确写「尚未开始写分析代码，四个方案不是已实现的东西」。
2. **数据渠道建议存在事实错误**。同一份讨论稿推荐「Hakush.in / Yatta.top 最推荐，10 分钟拿到」，
   但也自注「我发现不太行」；推荐的 BeautifulSoup `p`/`tr` 提取法对 BWiki **完全不成立**
   （该页正文是 SMW `#ask` 服务端渲染结果，没有表格）。修正：转入 `01-source-research.md`
   的逐渠道实测，避免沿用讨论稿的想当然结论。
3. **「先选一个方案」的思维误区**。最初想直接拍板方案 2（难度低、图好看），
   但评审发现真正的瓶颈不在算法而在数据准备。修正：把「选方案」改成「先补齐四方案共同前置」，
   项目范围因此收敛为语料工程，避免了在脏数据上做分析、结论站不住的风险。
4. **范围一开始想「尽量全」**（主线+活动+支线）。评估后发现范围越大时间线越不可靠、
   清洗成本线性上升，且课程报告不需要全量。修正：一次性砍到 67 页主线，并在文档里冻结范围。
